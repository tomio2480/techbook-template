# prh 加算辞書による読点の検出

読点「、」を機械で検出する手段を用意した際の判断と検証を記録する．
caller 側で辞書を置き換える案を捨て，中央へ加算方式を提案して実装させた．
対象は Issue #99，PR #114，上流 `tomio2480/github-workflows#91`（`v2.7.0`）である．

## 背景

句点「。」は `ja-no-mixed-period`（`periodMark: "．"`）が検出する．
読点「、」には対応する規則が無く，#90 で見つけた混在は CI を通り続けていた．
CI は `filter-mode: added` で差分行しか見ないため，既存行の混在は表に出ない．

Issue #99 は 3 案を並べていた．caller ルートへ `prh.yml` を置く案 1，
中央へ読点規則を足す案 2，何もしない案 3 である．
前日の調査で案 1 は追随を失うと分かり，案 2 は「、」を使う caller を縛るため通らないと見た．
代わりに独自の検査スクリプトを置く第 3 案を用意していた．

## 上流を先に直す判断

第 3 案は採らなかった．着手前に上流の仕組みを見直した結果，第 4 の道があった．

- 中央 action は `prh.yml` を 1 本だけ解決する．
  一方 `.textlint-allowlist.yml` は inline で加算する．
  この「caller が中央へ足す」設計は既に受け入れられていた．
- `textlint-rule-prh` の `rulePaths` は配列である．
  中央と caller を並べれば，置き換えずに済む．
- 中央は仕組みだけを持ち，読点の規則は caller が持つ．
  そのため「、」を使う caller を縛らず，案 2 の欠点も消える．
- 独自スクリプトはコードブロック・インラインコードの除外を自前で書くことになる．
  prh は textlint の `Str` ノードだけを見るため，その除外を無償で得られる．

判断の基準は「どこで直せば全 caller が同じ恩恵を受けるか」である．
自リポジトリで完結させる方が速いが，同じ不足は他の caller にも残る．
中央の判断者が同一人であり，先方の判断待ちが障害にならない点も後押しした．

## 加算方式の設計

上流は `v2.7.0` で `.prh-extra.yml` として実装した．
caller root に置くと `rules.prh.rulePaths` が `[中央 prh.yml, 本ファイル]` の 2 本になる．

表 1. 設定ファイルの扱い

| ファイル | 中央との関係 | 用途 |
|---|---|---|
| `prh.yml` | 置き換え | 中央規則そのものを変えたいとき |
| `.prh-extra.yml` | 加算 | caller 固有の表記ゆれを足すとき |
| `.textlint-allowlist.yml` | 加算 | 個別の語や形を指摘から外すとき |

衝突は先に並ぶ中央辞書が勝つ．加算辞書から中央規則は弱められない．
本リポジトリが足したのは新規の規則 1 本のみで，衝突は起きない．

## 除外は鍵括弧で囲んだ 1 字に限る

規則を入れると，字種そのものを話題にする地の文が引っ掛かる．
`CLAUDE.md` と `docs/notes/` は旧字種を引用して規約と経緯を書くためである．

`.textlintignore` でファイルごと外す案は採らない．文長や助詞重複の検査まで失う．
除外は `.textlint-allowlist.yml` の 1 行に絞った．

```yaml
- "/「[、。]」/"
```

鍵括弧で 1 字だけ囲んだ形に限るため，区切りとして使われた「、」の検出は残る．
句点側は現時点で発火しないが，文末が「。」で終わる引用に備えて対にした．

## 設定の効き目を数える手順

CI が緑でも設定が効いた証拠にならない．`filter-mode: added` では既存行の指摘が出ない．
手元で全量を検査し，除外が何を隠しているかを数えた．

再現は中央の `generate-textlint-runtime.py` を取得し，
CI と同じ引数で runtime config を生成する．自作の設定を組むと，
思い込みで CI と違うものを検査してしまう．

- `npx textlint` は動かない（`could not determine executable`）．
  `node node_modules/textlint/bin/textlint.js` を直接呼ぶ．
- 効き目は「入れた場合」と「抜いた場合」の 2 回実行し，件数差で示す．
  追加した allow が隠した指摘は全 Markdown で 5 件（110 件から 105 件）．
  いずれも `docs/notes/` の「、」言及だった．
- 出力を素朴に比較すると差分がずれる．stylish は同一ファイル内に修正可能な指摘があると
  列幅を変えるため，同じ指摘が別行に見える．空白を正規化してから比べる．

発火側は fixture で確かめた．地の文の読点だけを検出し，鍵括弧の言及・
インラインコード・コードブロックは検出しない．
同一行に言及と実違反が並ぶ場合も，実違反だけを検出した．

マージ前の最終確認は CI ログの 3 行で行う．
どのファイルが実際に注入されたかが分かる．

```text
caller allowlist:    .../.textlint-allowlist.yml
caller prh extra:    .../.prh-extra.yml
prh dictionary:      .../templates/prh.yml
```

## 辞書自身に自己検査を持たせる

prh の `specs` は `from` と `to` の組を書くと，辞書の読み込み時に検証される．
期待どおり変換できなければ textlint が落ちる．

```yaml
specs:
  - from: 前段であり、後段である
    to: 前段であり，後段である
```

故意に `to` を壊すと `spec failed` で読み込みに失敗することを確認した．
辞書が壊れたまま素通りしない．規則を足すたびに `specs` も足す．

## 規約を書き足す

`CLAUDE.md` は句点だけを規定し，読点は慣行のままだった．
Issue #101・#102 で「，」へ統一したが，文書には残っていなかった．
検出手段を入れる機会に，規約と検出手段の対応を明記した．

規律を機械で強制するときは，規律の文書と検出の設定を同じ PR で揃える．
片方だけ入れると，後から来た者がどちらを正とするか判断できない．
