# veraPDF 検証の CI 自動化で得た知見

Issue #189／PR #191 のセッションで得た知見を記す．
主な内容は 3 つある．非ブロッキング検証の設計判断と，
実物から構造を辿る規律の適用例と，CodeQL の失敗の見分け方である．

## 目次

- 非ブロッキング検証の設計
- 実物から構造を辿る
- CodeQL の数秒失敗は 2 種類ある
- Docker イメージのピン留め
- 参照

## 非ブロッキング検証の設計

現行出力は Tagged PDF の下地であり，PDF/UA-1 の完全準拠ではない．
合否でビルドを止めると，上流の出力次第で恒久的に赤へなりうる．
そこでレポート提供のみとし，実行エラーだけを失敗させた．

veraPDF の終了コードは公式文書に載っていない．0 が準拠，1 が非準拠，
2 以上が実行エラーである（veraPDF-library#1562 から）．
0 と 1 を成功へ束ね，2 以上で失敗させる形は，
非ブロッキング検証の型として再利用できる．

artifact の保存は要約の生成より先に置く．
要約が失敗してもレポートが残り，調査材料を失わないためである．
セルフレビューの一次走査が指摘し，順序の入れ替えで解決した．

## 実物から構造を辿る

veraPDF の JSON レポート構造は公式文書に載っていない．
推測の fixture では書かず，実レポートを先に取得した．
ローカルへ veraPDF を導入して実行し，構造を辿ってからテストを書いた．
CI 側でも artifact のレポートを取得し，同じ要約スクリプトへ通して
裏取りした．環境により数値は揺れたが，構造は同じだった
（失敗チェック数はローカル 738・CI 756）．

導入前の安全確認は，公式サイトの同一 URL から独立に再取得した
zip とのハッシュ照合で行った．チェックサムの公開が無い配布物でも，
この形なら取得経路での改変の有無を確かめられる．

## CodeQL の数秒失敗は 2 種類ある

前セッションではランナー障害の `startup_failure` が数秒の失敗として
現れた．今回の 3 秒失敗は実指摘（`js/incomplete-sanitization`・HIGH）
だった．所要時間だけで障害と断定せず，check-run の出力を読んでから
判断する．

指摘の内容は，表セルの `|` エスケープで `\` を先に畳んでいない点で
ある．順序が逆だと元の `\` と挿入分が合成され，Markdown で素の `|`
へ戻って表が崩れる．エスケープは対象文字より先に，エスケープ文字
自身を畳む．

## Docker イメージのピン留め

workflow 内の `docker run` が参照するイメージは Dependabot の追跡
対象外である．docker エコシステムを足しても Dockerfile しか見ない．
タグは書き換え可能なため，ダイジェストでピン留めした．
更新は手動になる．この制約はコメントとして workflow へ残した．
