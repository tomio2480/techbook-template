# ページ数の検査が壊れていた件と，レビュー 11 巡の経過

テーマ CSS へ 2 規則を足しただけの変更で `npm run build:print` が落ちた．
原因は変更側ではなく，ページ数を数える検査の側にあった．
本稿はその切り分けの手順と，codex のレビューが 11 巡に及んだ経過を残す．
対象は Issue #130・#145，PR #146・#147 である．

## 目次

- 症状と最初の見立て
- 切り分けの手順
- 本当の原因
- レビュー 11 巡で分かったこと
- 次に同じ場面へ出会ったら

## 症状と最初の見立て

`theme.css` へ `.term > p` と `figure img.on-white` を足し，第 2 章へ使用例を
置いた．`npm test` と `npm run build` は通る．`npm run build:print` だけが
次の 2 行で落ちた．

```text
検証失敗: 総ページ数が想定と異なります（実際 34・想定 36）。テーマ CSS の改ページ指定を print-measure.css が打ち消せていない可能性があります。
検証失敗: 総ページ数 34 が 4 の倍数になりませんでした。
```

メッセージは測定パスと本番パスの食い違いを疑わせる．
実際，足した内容にはコラムの中の図があり，`break-inside: avoid` を持つ枠が
大きくなる．測定パスと本番パスで組版結果が変わったと考えるのが自然に見えた．

**この見立ては外れていた．**

## 切り分けの手順

### 1. 変更の有無で比べる

作業ツリーを退避して `main` そのままでビルドし直した．
36 ページで正常終了した．変更が引き金であることは確かめられた．

### 2. 出力そのものを数える

失敗したビルドが残した `dist/book-print.pdf` を PyMuPDF で読むと **36 ページ** あった．
1 ページずつ本文を出すと，表紙から裏表紙まで計画どおり並んでいた．
つまり組版は正しく，誤っていたのは数える側である．

ここが分かれ目だった．エラーメッセージの示す方向（組版）を疑い続けると，
`break-inside` や `print-measure.css` をいくら見ても原因へ届かない．
**失敗したときは，まず出力そのものを別の道具で測る．**

### 3. 内部構造を突き合わせる

`scripts/count-pdf-pages.mjs` を実際の PDF へ当てると 34 を返した．
オブジェクトの見出しから `/ObjStm` を列挙すると 54 本あった．
`/Length` で取り出せば全て展開できる．
一方，既存の取り方では 53 本しか展開できない．
取り逃した 1 本にページツリーのルート（`/Count 36`）とページ 2 個が入っていた．

## 本当の原因

ストリームの終わりを `endstream` の検索で決め，直前の改行を
`/\r?\n$/` で削っていた．取り逃したストリームは次の形だった．

```text
data last bytes: 97 8c 4d 0d   separator: 0a
```

圧縮データの最後のバイトが CR（`0x0d`）であり，続く区切りの LF と合わせて
CRLF と読まれる．データの最後の 1 バイトまで削れ，展開に失敗する．
`0x0d` は zlib の末尾 4 バイト（adler32）の一部であり，中身しだいで現れる．
`main` では現れず，原稿を変えた結果として表面化した．

ページツリーのルートを読めないと，数え上げのフォールバックへ落ちる．
そこは平文と復号側の一方だけを見るため，34 という中途半端な値を返した．

要点は次の 2 つである．

- **ストリームの範囲は `/Length` で決める．** 区切りの推定に頼らない．
- **入稿の可否を左右する検査ほど，出力を別の道具で裏取りする．**
  この検査が黙って通れば，誤ったページ数のまま入稿しかねなかった．

## レビュー 11 巡で分かったこと

修正 PR（#146）へ codex のレビューを 11 巡かけ，12 件の指摘へ対応した．
指摘は次のように進んだ．

| 巡 | 指摘の要点 |
|---|---|
| 1 | 入れ子辞書を持つ `/ObjStm` を取り逃す |
| 2 | 入れ子の `/Length` を誤採用／見出しに見える文字列で辞書が切れる |
| 3 | 文字列中の `>>`／見出し直後のコメント |
| 4 | 辞書内コメントの `>>`／文字列中の `/Length`／`stream` 探索の窓 |
| 5 | 見出しの数値の間のコメント |
| 6 | 配列値の中身をキーとして拾う |
| 7 | 配列走査で `<<` の 2 文字目を 16 進文字列と誤認 |
| 8 | NUL が空白扱いされない／間接 `/Length` での CR 末尾 |
| 9 | 同一ストリームの二重展開 |
| 10 | NUL 区切りの間接 `/Length` |
| 11 | 指摘なし |

12 件はばらばらの不具合ではない．いずれも
**PDF の字句規則へ沿わずに文字列を探していた** ことから出ている．
巡ごとに当て込みで直すと，隣の構文で同じ形の指摘が返ってくる．

収束したのは，個別の当て込みをやめた 4 巡目以降である．
空白・コメント・文字列リテラル・16 進文字列・配列・辞書を同じ規則で
読み飛ばす走査へ整理し，読み飛ばした跡へ空白を 1 つ置く形にそろえた．
10 巡目の指摘（NUL 区切りの `/Length`）を受けたときは，
空白の定義を定数へ切り出して全ての照合をそこから組み立てた．
同種の取りこぼしが他のキーで再発しないようにするためである．

7 巡目の指摘は自分の実装バグだった．配列を読み飛ばすとき 1 文字ずつ見ており，
`<<` の 2 文字目を 16 進文字列の始まりと取り違えていた．
**前の巡で足した処理が次の巡の指摘を生む** ことがある．
巡が進んでも，足したコードは同じ厳しさで見直す．

指摘のうち，実際の PDF で起きるものは 1 件目だけである．残りは仕様上ありうる形で，
本テンプレートの出力では起きない．それでも直した理由は次の 2 つである．

- 直す手間が小さい（多くは数行）．
- 検査の誤りが入稿の事故に直結する．黙って通る失敗は避けたい．

一方で，間接参照の `/Length` を参照先まで引きに行く案は採らなかった．
番号でオブジェクトを探す走査が要り，ページ数を数えるという目的に対して重い．
終わりの候補を確からしい順に試し，展開の成否で決める形にとどめた．
**採らなかった案は，理由を添えて返信へ残す．**

## 次に同じ場面へ出会ったら

- ビルドの検査が落ちたら，まず **出力を別の道具で測る** ．
  エラーメッセージの指す方向が正しいとはかぎらない．
- 変更の有無で比べ，引き金と原因を分けて考える．
  引き金が変更側でも，原因が変更側とはかぎらない．
- バイト列を扱うコードでは，区切りを推定せず宣言された長さを使う．
- レビューが同じ形の指摘を繰り返すなら，当て込みをやめて
  規則そのものへ寄せる．巡数はそこから減る．
