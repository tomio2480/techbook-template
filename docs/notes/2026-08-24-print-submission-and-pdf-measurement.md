# 紙入稿の雛形と，PDF を測るときの落とし穴

入稿要件の雛形を置く作業（Issue #140・PR #161）で得た知見を残す．
雛形へ何を書き，何を書かないかの判断と，PDF を測って裏を取る手順を扱う．
測定では 2 度読み違えた．どちらも「数える対象を絞っていない」ことが根であった．
あわせて codex のレビュー 3 件が同じ根から出ていた経過を記録する．

## 目次

- 雛形は値を持たない
- 又聞きを実測へ置き換える
- 参照されないオブジェクトを数えていた
- 「埋め込まれていない」は読み違いだった
- レビュー 3 件の共通の根
- Issue #141 の前提は実測で否定されている
- 次に同じ場面へ出会ったら

## 雛形は値を持たない

入稿の要件は印刷所ごとに違う．解像度・塗り足し・ページ数の単位・
ファイル名の規則が，いずれも先方の資料に散っている．
本テンプレートが特定の印刷所の数値を持つと，別の印刷所を使う利用者を誤らせる．
要件は改訂もされる．

そこで `docs/spec/print-submission.md` は **枠組みだけ** を持つ．
項目の一覧・表の枠・測る観点を置き，数値は書籍側で埋める．
要件の欄の括弧書きは記入の目安であり，特定の印刷所のものではない．

節の構成は Issue の提案（4 節）より多い 9 節とした．
要件の表が出典の番号を指すため，出典の節が対になる．
用語集を置いたのは，表紙の面の呼び方（表 1 から表 4）と，
文書側の表番号が紛れるためである．同じ「表 2」が別のものを指しかねない．

## 又聞きを実測へ置き換える

観点に添えた「見落としやすい点」は，はじめ派生リポジトリの記述から写した．
対象は `techbook-introduction-to-electronics-basic-led` である．
写したまま置くと，読み手には本テンプレートで確かめた事実に見える．

`npm run build:print` を走らせ，出力を測って 3 点を確かめた．

- `MediaBox` は 188 x 263 mm，`TrimBox` は 182 x 257 mm である．
- 和文は Type 3（輪郭）として入る．`FontFile` を持たない．
- 装置依存の色空間を持つ点画像が混じる．

透明の数え方だけは手元で再現できなかった．出所を派生リポジトリと明記した．

測定には `node_modules/pdf-lib`（1.17.1）を使う．
スクラッチパッドの `.mjs` から絶対パスで `import` すれば，リポジトリを汚さない．
`PDFDocument.getPage()` はタグ付け後の PDF で落ちる．
`enumerateIndirectObjects()` から `/Type /Page` を拾う形にした．

## 参照されないオブジェクトを数えていた

その `enumerateIndirectObjects()` が `/Type /Page` を 54 個返した．
ビルドの報告は 36 ページである．食い違いを「差し替え前の古い版が残るため」と
書いたが，機構を確かめていなかった．

確かめると増分更新ではない．`%%EOF` は 1 つしかない．
素のバイト列に現れる `/Type /Page` も 36 個で，ページツリーの `/Count` も 36 である．
つまり **ページツリーから参照されないページオブジェクトが 18 個残っている．**
タグ付けの工程が置き去りにしたものと見られる．

数える対象を絞れば起きない．ページツリーか `Resources` から辿る．

## 「埋め込まれていない」は読み違いだった

同じ原因で，もう 1 つ読み違えた．
`Type0` の子孫フォントを辿ると Consolas が「埋め込みなし」と出る．
コード用の書体が埋め込まれていないなら，入稿で問題になる．

素のオブジェクトから `/FontName` と `/FontFile` の対応を数え直すと，
`DAAAAA+Consolas` は `FontFile2` を持っていた．埋め込みは正常である．
`FontFile` を持たないのは和文（Noto Sans JP・Noto Serif JP）と MathJax で，
いずれも Type 3 の輪郭として入る．欠落ではない．

見分ける手がかりは残った．**同じ書体が「あり」と「なし」の両方で出たら，
参照されないオブジェクトを数えている疑いを持つ．**

## レビュー 3 件の共通の根

codex の 1 巡目は 3 件（いずれも P2）を返した．対象はすべて測り方の表である．

- `MediaBox` と `TrimBox` の差を塗り足しの量と書いた．
  差は 6 mm であり，1 辺は 3 mm である．要件と直に比べると誤判定する．
- 色空間を「プロファイルを見る」と書いた．
  `DeviceRGB` はプロファイルを持たない．同じ文書に「装置依存の色空間で入る」と
  書きながら，その画像を数えない手順になっていた．
- 透明を「指定を数える」と書き，隣へ「過大に数える」と添えた．

3 つの根は同じである．**判定に使えない手順へ注意書きを添えて済ませていた．**
注意書きは手順の欠陥を埋め合わせない．手順そのものを判定できる形へ直す．
`/None` でない `SMask` と，1 未満の `ca`・`CA` だけを数える，という形である．

自分の測定スクリプトは，はじめからこの絞り込みを書いていた．
書いた手順のほうが，実際に動かした手順より粗かった．

## Issue #141 の前提は実測で否定されている

派生リポジトリの `docs/spec/print-submission.md` を読む過程で分かった．
Issue #141 が挙げる「表紙を抜くと本文は 62 ページとなり，4 の倍数を外れる」は
誤りである．先方の実測では表紙込み 64 ページ，表紙なし 60 ページであった．
表紙を抜くと後続の面がずれ，改丁の調整も変わるためである．

`print.cover.include` と `npm run build:cover` は先方に実装済みである．
Issue #141 は新規の設計ではなく，還元の作業にあたる．
着手時は本文の訂正から入る．

## 次に同じ場面へ出会ったら

- 又聞きの観察を仕様書へ書くときは，出所を明記するか，手元で測り直す．
- PDF を数えるときは，対象をページツリーか資源から辿る．
  総なめの件数は，ビルドの報告や `/Count` と突き合わせる．
- 「過大に数える」と断りたくなったら，その手順は判定に使えない．
  断り書きではなく，絞り込みを手順へ入れる．
