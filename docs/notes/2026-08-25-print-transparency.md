# 紙入稿データから透明効果を取り除いた記録

紙入稿用 PDF と表紙単体の入稿データから透明効果を外した経緯をまとめる．
発生源が 3 つあったこと，焼く色を計算では決められなかったこと，
検査を置く位置で見る対象が変わることを記録する．

## 背景

`docs/spec/print-submission.md` は透明効果を入稿要件の項目に挙げていた．
測り方も書いてあったが，取り除く実装は無かった．
派生リポジトリ `techbook-introduction-to-electronics-basic-led` が
先に手を付けている（PR #278）．
本作業は，その判断を上流へ引き取るものである．

引き取りにあたって前提が 2 つ食い違った．

- 派生側は `.tips` と `.caution` の 2 種を焼いていた．
  テンプレートには `.note` が残っており，3 種すべてが対象になる．
- 派生側の記録は枠アイコンだけを発生源として挙げていた．
  テンプレートでは表紙背景 SVG とコードハイライトも発生源であった．

## 判断

### 発生源で取り除く

<!-- textlint-disable ja-technical-writing/ja-no-mixed-period -->

表 1. 透明効果の発生源と取り除き方

<!-- textlint-enable ja-technical-writing/ja-no-mixed-period -->

| 発生源 | 実体 | 取り除き方 |
|---|---|---|
| 枠アイコン（Tips・注釈・注意） | CSS の `mask` と `opacity: 0.12` | 焼いた線画を `print.css` で背景に敷く |
| 表紙・裏表紙の背景 | SVG の `opacity`（6 種類の値） | 合成後の色を素材へ直接書く |
| コードハイライトの名前空間 | CSS の `opacity: 0.8` | 指定そのものをやめる |

素材（SVG）は素材そのものを焼き，紙用の写しを持たない．
一方でアイコンは紙用の CSS でだけ置き換え，テーマ本体は
意味トークンを参照したまま残す．扱いを分けた理由は次のとおりである．

- 素材を 2 つ持つと，片方だけを直したときに誌面が食い違う．
  食い違っても両方のビルドが成功するため，誰も気づかない．
- アイコンは同じテーマの中に 2 か所並ぶだけであり，
  形の一致を機械で検査できる．検査があれば食い違いは残らない．
- アイコンを焼くと配色替えへ追従しなくなる．
  電子書籍用を意味トークンのまま残せば，この代償は紙用だけで済む．

### 名前空間の淡色化はやめる

Prism の既定テーマは名前空間を `opacity: 0.8` で淡くする．
本テーマの取り決めは，シンタックス色が背景に対して
コントラスト比 4.5:1 以上を保つことである．
不透明度はこの比を検査の外側で崩す．紙で透明を持てない事情と併せて，
淡色化そのものをやめた．名前空間は地の文と同じ色で刷る．

この指定は現状の PDF には現れていなかった．
テンプレートの作例に該当するコードが無いためである．
残しておくと，利用者が名前空間を含むコードを載せた時点で
ビルドが止まる．発現を待たずに外した．

### 検査はタグ付けの後に置く

`scripts/tag-pdf.mjs` はタグ付けした写しで `dist/` の PDF を置き換える．
既存の検査群（ページ数・寸法）はタグ付けの前に走る．
透明効果の検査を同じ位置へ置くと，入稿へ渡らないファイルを見ることになる．
検査はタグ付けの後に置いた．

### 淡い塗りは明度段と別の区分にする

`scripts/check-diagram-luminance.mjs` へ `DIAGRAM_WASH_COLORS` を足した．
既定は空である．テンプレート同梱の図版は `led-circuit.svg` だけであり，
面を塗る下地を持たない．本ごとに足す口として置く．

派生側の記録が指摘するとおり，この検査は `fill-opacity` を読まない．
塗りを透明で薄めると，指定値だけを見て通り，実際に刷られる色を見逃す．
焼いて登録すれば盲点が塞がる．

## 測って初めて分かったこと

### 合成の結果は計算で決められない

焼く色は組版と同じ Chromium で描いて測った．
計算値（`round(前景 × α + 背景 × (1 - α))`）と食い違う箇所がある．

<!-- textlint-disable ja-technical-writing/ja-no-mixed-period -->

表 2. 計算値と実測値の食い違い

<!-- textlint-enable ja-technical-writing/ja-no-mixed-period -->

| 対象 | 前景と不透明度 | 背景 | 計算値 | 実測値 |
|---|---|---|---|---|
| 枠アイコン | `#2f5b8c` 0.12 | `#ffffff` | `#e6ebf1` | `#e6ebf1` |
| 天の帯 | `#b0c4de` 0.4 | `#f0f4f8` | `#d6e1ee` | `#d6e0ee` |
| 地の帯 | `#2f5b8c` 0.85 | `#f0f4f8` | `#4c729c` | `#4c719c` |
| 裏表紙の帯 | `#b0c4de` 0.35 | `#f0f4f8` | `#dae3ef` | `#dae4ef` |

ずれは 1 階調にとどまるが，向きは一定しない．
明るい側へ外れる場合も暗い側へ外れる場合もある．
premultiplied な 8 ビット合成の丸めを再現しようとしたが，
すべての事例に合う式には至らなかった．計算では決めない．

派生リポジトリの記録は，枠アイコンの実測値を `#e7ecf2` としている．
本リポジトリの実測は `#e6ebf1` であり，計算値と一致した．
測る経路の違いによるものと見て，本リポジトリは自前の実測値を採る．

この食い違いは検査の設計にも効く．
`scripts/check-icon-bake.mjs` は焼いた色を計算値と突き合わせるが，
完全一致では見ない．2 階調までのずれを許す．
焼き忘れは桁違いに大きく離れるため，この幅でも捉えられる．

### 裏表紙の透明はすでに消えていた

表紙は `cover.md` の `img` として敷くため，PDF へベクターのまま入る．
`opacity` は `/ca` として残っていた．
裏表紙は `@page back-cover` の CSS 背景であり，
Chromium が塗りつぶした点画像へ平坦化する．
透明はその過程で消え，PDF には現れていなかった．

つまり裏表紙の SVG を焼かなくても，検査は通っていた．
それでも焼いた．表 1 と表 4 は対になる素材であり，
片方だけ透明を持つ状態は，差し替える利用者にとって罠になる．

### 同じ指定が平文と圧縮側の両方に現れる

出来上がった PDF では，同じ `ExtGState` が平文の間接オブジェクトと
オブジェクトストリームの両方に現れた．
発生源 6 個に対して検出は 12 件であった．

件数は発生源の数と一致しない．検査は 0 件かどうかだけを見る形にした．
入稿データに透明の指定が 1 つも無い状態を求めるためであり，
参照されないオブジェクトまで数える側へ倒している．

### 焼いた線画は点画像にならない

データ URI の SVG を `background-image` で敷いても，
PDF には画像オブジェクトが 1 つも現れなかった．
`mask` で敷いていたときと同じくベクターのまま入る．
表紙背景で起きる 72 dpi への平坦化は，
ラスターやグラデーションを含む大きな SVG に固有の現象である．

### 重なりの下は焼くと消える

表紙の円は，地の罫線と帯の下へ回り込んでいる．
焼いた後はその重なりが消える．
明るくなる量は罫線が 6 階調，帯が 3 階調である（いずれも R チャンネル）．
重なりを保つには曲線に沿った分割が要る．
差は肉眼で追えない大きさであり，分割はしなかった．

### 数える対象は不透明度だけではない

初版の検査はソフトマスクと定数アルファだけを見ていた．
`/BM /Multiply` は `ca`・`CA` を 1 に保ち，ソフトマスクも持たないまま
下の絵柄と混ぜて刷らせる．利用者が `mix-blend-mode` を書けばこの形になる．
`/SMaskInData` も同じく，画像が自ら持つ透明を使うと宣言する．
どちらも数える対象へ加えた（PR #170 の Codex レビュー指摘による）．

`/BM` の値が名前として読めない形（配列・間接参照）は，不透明と示せない．
読めないまま通すと，取り除いたつもりの透明が入稿データへ残る．
数える側へ倒した．

透明グループ（`/Group << /S /Transparency >>`）は数えない．
合成の場を宣言するだけであり，そこで透明を使う要素は他の 4 つが捉える．
実測では紙用と表紙の PDF に 0 件，電子書籍用に 5 件あった．
付いていること自体は違反の証拠にならない．

### 素のバイト列への正規表現は両方向に外す

初版は PDF 全体へ正規表現を当てていた．2 つの取り違えがある
（PR #170 の Codex レビュー指摘による）．

- 誌面の文字列や読み上げ用の代替テキストに `/ca 0.5` と書くと，
  指定と取り違えて失敗する．技術書の本文は，まさにこの並びを書きうる．
- 鍵と値のあいだにはコメントを置ける．`/ca%注記\n0.5` を読み落とす．

走査を辞書の単位へ改めた．圧縮側はオブジェクトストリームを展開し，
文字列とコメントを飛ばして辿る．辞書を読む部品は
`count-pdf-pages.mjs` から export して共有する．

平文側は 2 段構えになった．最初は `obj` を語として探す形にしたが，
これも取り違える．誌面の文字列やストリームの中に `obj << /ca 0.5 >>` と
書かれた並びを，本物の見出しと読んでしまう．
PDF の書き方そのものを解説する原稿は，まさにこの並びを載せうる．

ファイルの本体を先頭から辿り，辞書を見つけたらその範囲だけを読む形へ改めた．
辞書の直後にストリームが続くなら，`/Length` から求めた終わりまで飛ばす．
ストリームは必ず辞書の後ろに置かれるため，辞書から辿れば取り違えは起きない．
飛ばさずに辿ると，データの中の `(` で同期を失って本物の指定を読み落とす．

**見出しの語を探す形は，2 度続けて誤りだった．** どちらも
「それらしい並び」を手掛かりにしており，PDF の構造を辿っていなかった．
構造を辿る形にして初めて，取り違えの筋が消えた．

改めた前後で，実物の PDF に対する判定は変わらなかった．
入稿データ 3 本はいずれも 0 件である．
電子書籍用は 6 件（SMask 4・アルファ 2）で，件数まで一致した．

## 採らなかった案

### SVG の透明を静的に検査する仕組み

素材へ `opacity` が戻ったことを，ビルドを待たずに検出する案があった．
作らなかった．PDF の検査が同じ誤りを確実に捉えるためである．
検査を二重に持つと，同じ趣旨の規律が 2 か所に散る．

ただし裏表紙のように，平坦化で透明が消える経路では PDF の検査が働かない．
この経路は素材のコメントと spec の記述で支えている．

### 紙用と電子書籍用で素材を分ける

電子書籍用の透明を残せるが，採らなかった．
理由は前掲のとおり，片方だけを直したときに食い違うためである．

## 測り方

実測には `playwright-core` を使った．手順で詰まった点を残す．

- `chromium.launch()` は既定で `headless_shell` を探す．
  本環境には `chromium-1161` だけが入っており，
  `executablePath` で実行ファイルを名指しする必要がある．
- `about:blank` へ `setContent` した頁からは `file://` の画像を読めない．
  SVG の中身を読み込んで直に埋め込む．
- 細い罫線は縁の混色を拾う．10 倍へ拡大して描き，中心を測る．
- 画面の合成と PDF の合成は別物である．
  PDF は `/ca` を持ったまま渡り，最終的な合成は表示側や出力機が行う．
  本記録の実測値は，あくまで組版エンジンの合成である．

検査の再現は次の 2 つで行える．

```bash
npm run check:icon-bake
```

```bash
npm run check:transparency dist/book-print.pdf
```
