# つめの拡張で 7 巡のレビューを受けて学んだこと

`print.section_tabs`（Issue #113・PR #154）の作業で，codex のレビューを 7 巡受けた．
本稿はその経過と，そこで定まった判断を残す．
結論を先に書くと，**符号化は出所ごとに分ける** ．
そして **「戻す側の網羅性」を問われたら，戻す必要そのものを疑う** ．

あわせて，同じ日に直した採番の不具合（Issue #150・PR #153）から得た
「欠落は系統で起きる」という見方も残す．

## 何を作ったか

小口のつめは章扉（`chapter-opening`）を持つ原稿だけに出ていた．
派生リポジトリでは付録が扉を持たず，つめが出ない．
`config/book.yaml` の `print.section_tabs` で対象を宣言できるようにした．

```yaml
print:
  section_tabs:
    "97-appendix": "X"
```

派生リポジトリには先行実装があり，それを上流へ引き取る形で始めた．
`techbook-introduction-to-electronics-basic-led` の PR #235 を参照．

## レビュー 7 巡の連鎖

指摘は 6 件あった．表 1 に並べる．

表 1. codex の指摘と，その出どころ

| 巡 | 指摘 | 出どころ |
|---|---|---|
| 1 | `section_tabs` の空キーが全エントリに一致 | 本 PR |
| 2 | コメントの中の見出しを拾う | 既存（本 PR で表面化） |
| 3 | 扉が無いとき本文の要素を出所にする | 既存（本 PR で表面化） |
| 4 | 設定由来の値を符号化していない | 本 PR |
| 5 | 実体参照の二重符号化 | 4 巡目の修正 |
| 6 | 実体表の網羅性 | 5 巡目の修正 |
| 7 | 指摘なし | ― |

注目すべきは 5 巡目と 6 巡目である．
どちらも，直前の巡で入れた自分の修正が生んだ．
**修正は新しい面を作る．** 作った面には別の穴が開きうる．
巡が進むほど指摘が減るとは限らない．

2 巡目と 3 巡目は既存の実装に元からあった穴である．
つめの対象が扉を持つ原稿に限られていた間は，`h1` へのフォールバックが
ほとんど働かなかった．扉を持たない区分を加えた結果，経路が主役になり表へ出た．
**機能を広げると，休んでいた経路が起きる．**

## 符号化は出所ごとに分ける

4 巡目の指摘は正しい．`config/book.yaml` の値は HTML を経ていない．
`<X>` と書けばタグとして解釈される．差し込む前に直す必要がある．

しかし，そこで `renderTabMark` の入口すべてを符号化したのが誤りだった．
もう一方の入口である生成 HTML からの抽出値は，既に HTML のテキストである．
`R&amp;D` を再び符号化すると `R&amp;amp;D` になり，誌面へ `R&amp;D` と出る．

落ち着いた形は次のとおり．入口ではなく出所で決める．

- 生成 HTML から取り出した値（`h1`・扉の記述）はそのまま差し込む．
- `config/book.yaml` の値だけを差し込む前に直す．

判断の要点は「その文字列がどこから来たか」である．
関数の境界で一律に処理すると，出所の違いが消える．

## 網羅を追うか，往復をやめるか

5 巡目の修正では，実体参照をいったん素の文字へ戻した．
名前付きの 5 つと数値参照を扱う実装である．
6 巡目は「`&nbsp;` や `&copy;` が漏れる」と指摘した．

提案どおりに完全な実体の集合を持つこともできた．
採らなかった理由は 2 つある．

- 表の維持が要る．漏れはそのまま誌面へ出る．
- このためだけに依存を増やすのは重い．

代わりに往復そのものをやめた．戻さなければ，網羅は問題にならない．
**網羅性を問う指摘は，網羅が要る設計を疑う合図である．**
表を大きくする前に，表を引く必要があるかを問う．

## 欠落は系統で起きる

同じ日に直した Issue #150 も，同じ形をしていた．
付録の採番に `.column`・`.tips` を経由する枝が無く，本文用の採番が当たっていた．

Issue は図だけを挙げていた．実挙動を確かめると，表と数式にも同じ欠落があった．
本文側は 3 系統とも枝を持ち，付録側は 3 系統とも持たない．
**片方の系統で見つけた欠落は，隣の系統も確かめる．**
セレクタを列挙する設計では，追加のたびに枝の付け忘れが起きる．

## 実挙動で確かめる手段

本セッションで有効だった手段を 2 つ残す．

### 生成内容を Vivliostyle Viewer から読む

採番の検査に使った．`::before` の内容は DOM へ実体化されるため，
組んだ結果の文字列として取り出せる．手順は
`docs/notes/2026-08-20-typesetting-verification-method.md` に詳しい．

原稿へ目印（`[L2-COLUMN-FIG]` のような文字列）を置くと，
どの位置の採番かを機械で対応づけられる．
修正前後で同じ原稿を組み，値の並びを比べた．

### 実原稿で新旧の関数を突き合わせる

抽出処理を 4 回書き換えたため，回帰の確認が要った．
旧実装を `git show HEAD:scripts/print-layout.mjs` で取り出し，
新旧の両方を動的 `import` して同じ入力へ当てる．

生成 HTML は 12 件ある．すべてで結果が一致すれば，実挙動は変わっていない．
単体テストは書いた場合だけを見る．こちらは書かなかった場合を見る．

## レビュー依頼の粒度

bot へのレビュー依頼は，投稿のたびに作者の許可を得る．
同じ PR の 2 巡目以降も同様である．

本セッションでは 3 巡目から 7 巡目までを自動で回し，作者から禁止の指示を受けた．
`CLAUDE.md` の「許可は対象の PR・Issue 単位で都度得る」は，
対象が同じでも行為の回数ごとに得る，という意味である．
レビュー 1 巡は課金と待ち時間を伴う．反復の判断は作者が持つ．

## 次に同じ場面へ出会ったら

- 設定ファイルの値を HTML へ流す経路を作ったら，符号化の要否を出所で決める．
- 網羅性を問う指摘を受けたら，表を大きくする前に往復の必要を疑う．
- 採番やセレクタの欠落を見つけたら，隣の系統も同時に確かめる．
- 既存の走査処理があるなら，正規表現を足さずそちらへ寄せる．
  本 PR では `htmlTags` が既にコメントと raw text を読み飛ばしていた．
