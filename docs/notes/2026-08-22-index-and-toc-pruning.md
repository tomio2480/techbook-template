# 解決できない target-counter は「??」を刷る．レビュー 4 巡の記録

索引を入れる作業（Issue #131・PR #156・#157）で得た知見を残す．
最大の発見は，解決できない `target-counter` がビルドを止めないことである．
`??` を刷ったまま成功する．入稿できてしまう失敗であり，止まるより悪い．
あわせて codex のレビュー 4 巡が同じ根から出ていた経過を記録する．

## 解決できない参照は「??」になる

索引のページ番号は `target-counter(attr(href url), page)` で解決する．
着手時は「参照先が無いと解決できず，描画が終わらない」という前提を置いた．
出所は `2026-08-20-typesetting-verification-method.md` の記述である．

**この前提は `vivliostyle build` では成り立たなかった．**

索引の原稿を消し，目次に古いリンクを残した状態でビルドすると，
17.6 秒で成功した．警告も出ない．誌面はこうなる．

```text
索引 ...............................??
```

索引の側でも同じである．アンカーを 1 つ壊すと「数式 ??」と刷られた．

ノートの記述が誤りとは限らない．あちらは Vivliostyle Viewer での観察である．
`window.coreViewer.readyState` が `complete` にならない話であり，
組版そのものが終わらないという意味ではない．
**ビューアと `vivliostyle build` は別の経路として扱う．**

## 検査が要る理由を書き違えていた

`docs/spec/index-page.md` と `README.md` に
「参照先が無いとビルドが終わらない」と書いていた．
実挙動を確かめる前に，ノートの記述をそのまま前提へ写したためである．

検査（`npm run check:index`）が要る理由は，止まるからではない．
**黙って通るからである．** 止まる失敗は誰かが気付く．
`??` を刷った PDF は，見落とせばそのまま入稿できる．
理由を取り違えると，検査の置き場所や強さの判断も変わる．

`2026-08-20-pdf-page-count-and-review-rounds.md` の
「黙って通る失敗は避けたい」と同じ話である．

## 目次に残る死んだリンク

索引を本から外す手順（原稿を消して `entry` から外す）を書いたが，
`src/chapters/toc.html` に索引の項目が残る．
`mergeTocTrees()` が old 側にのみ残った項目を手動追加として残す仕様のためである．
残った項目は消えた原稿を指し，`??` を刷る．

`pruneDeadTocEntries()` を足し，本に含まれない原稿を指す手動追加の項目を
落とすようにした．手で書いた文言を残す性質は保つ．

## レビュー 4 巡の共通点

codex のレビューは 4 巡・5 件に及んだ．内訳は次のとおり．

表 1. レビューの巡と指摘の要点

| 巡 | 指摘 | 私が置いていた妥協 |
|---|---|---|
| 1 | 索引を外すと目次に項目が残る | 手順の文書化で足りると考えた |
| 2 | 生きた原稿の一覧を生成物から引くな | 生成された目次で代用した |
| 3a | コメントアウトした entry を数える | 設定を文字列として読んだ |
| 3b | 手動項目の子が落ちない | 最上位だけを対象にした |
| 4 | 子を落とすと親の属性が消える | 属性の欠落を許容した |

**5 件とも，私がどこかで妥協を置いた箇所である．**
指摘の内容はばらばらに見えるが，根は 1 つに絞れる．

- 1〜3a は「本に含まれる原稿か」の判定の出所である．
  生成 HTML の有無・生成された目次・設定ファイルの文字列と 3 回ずらし，
  ようやく `import()` した `entry` の値へ落ち着いた．
- 3b・4 は「手動追加を残す」という約束をどこまで守るかである．
  子孫を対象外にし，属性を捨て，2 度削った．

前巡の修正が次巡の指摘を生む形も再現した．
`rawOuterHtml` を捨てる修正（3b）が，属性の欠落（4）を招いている．
`2026-08-20-pdf-page-count-and-review-rounds.md` の
「前の巡で足した処理が次の巡の指摘を生む」と同じである．

指摘の見立てが外れることもあった．
1 巡目の「組版が止まる」は再現しなかった．
2 巡目の「見出しを持たない原稿は生成 nav に載らない」も外れである．
`back-cover.md` は見出しを持たないが nav に並ぶ．
それでも 2 巡目は指摘の向きへ直した．理由は別にある．
生成物の作られ方は実装しだいであり，そこへ判定を預けると，
将来の変更で追跡ファイルを壊しかねないためである．
**外れた前提は外れたと返し，採る理由は自分の言葉で書く．**

## 次に同じ場面へ出会ったら

- **ノートの記述も前提として確かめる．** 自分たちの記録でも，
  観察した状況（ビューアか，ビルドか）が違えば結論は変わる．
- **仕様に「なぜ検査するか」を書くときは実挙動で裏を取る．**
  理由を取り違えると，後から読む人の判断もずれる．
- **判定は生成物ではなく設定から引く．** 生成物は実装の都合で変わる．
  設定は人が書いた意図そのものである．
- **妥協を残すなら，その場で潰す．** 実害は小さいと書いた箇所は，
  次の巡で指摘として返ってくる．
- 追跡ファイルを書き換える処理では，壊す向きの間違いを避ける．
  消しすぎと残しすぎのどちらが取り返しにくいかで判断する．
