# 開き括弧の直後に置いた数式で行末禁則が破れる件

開き括弧の直後にインライン数式を置くと，開き括弧だけが行末へ残る（Issue #134）．
最小構成で再現し，真因が文字クラスではなく分割できない塊の直前にあると確かめた．
Issue が未検証としていた `line-break: strict` は効かない．
テンプレートでは執筆の規律で防ぐ方針を採る．

## 目次

## 症状

派生リポジトリ `techbook-introduction-to-electronics-basic-led` の誌面で 1 件出た．
原稿は次のとおりである．

```markdown
「$I_v = 70\ \mathrm{mcd}$（$I_F = 20\ \mathrm{mA}$）」は，…
```

組み上がりでは行が `…（` で終わり，次の行が `IF = 20 mA）」は，` から始まる．
括弧の種類は関係しない．語順を変えて `（` を避けると，今度は `「` が同じ位置に残った．

## 最小構成での再現

`npm run build:print` は 1 回およそ 4 分かかる．
素の HTML と Vivliostyle CLI だけの検体なら 1 回およそ 20 秒で済む．
幅 20em の段落へ，括弧の前に置く文字数を 12 字から 22 字まで変えた検体を並べた．
検体 1 種につき 11 件である．

表 1. 最小構成での検体と結果

| 検体 | 括弧の直後に置いたもの | 行末に「（」が残った件数 |
|---|---|---|
| span | 素のインライン要素（中に空白があり内側で改行できる） | 0 |
| atomic | 分割できない塊（`display: inline-block` と `nowrap`） | 6 |
| strict | atomic と同じ．段落へ `line-break: strict` を併用 | 6 |
| nobr | atomic を括弧ごと `white-space: nowrap` で括る | 0 |
| text | 素のテキスト（対照） | 0 |

VFM は `$…$` を `<span class="math inline">` へ変換し，MathJax が組版する．
組版後の数式は内側で改行できない塊になるため，検体 atomic がこの状態に当たる．

## 分かったこと

改行位置の選択は，直前の文字クラスではなく塊の分割可否で決まっている．
中で改行できるインライン要素（検体 span）では起きない．
塊が行に収まらないとき，Vivliostyle はその直前を改行位置に選び，
手前の文字が開き括弧かどうかを見ない．

UAX #14 では開き括弧（`（` は OP クラス）の直後を改行禁止としている．
Vivliostyle はこの禁止を，分割できない塊の直前では適用していない．

`line-break: strict` は効かなかった．
同ルールは文字クラスの扱いを厳しくするものであり，塊の直前の判定には届かない．
Issue #134 は案 3 を未検証としていたが，ここで否定できる．

## 案の比較と採用

表 2. 対処案と採否

| 案 | 内容 | 効果 | 採否 |
|---|---|---|---|
| 1 | 執筆の規律として `README.md` へ書く | 原稿の書き方で防げる | 採用 |
| 2 | `.nobr { white-space: nowrap; }` を持たせて括弧ごと括る | 防げる | 見送り |
| 3 | `line-break: strict` をテーマへ入れる | 効かない | 棄却 |

案 1 を採る．副作用が無く，量記号の前へ語を補うと読みやすさも上がるためである．
案 2 は効くが，原稿へ HTML を書く手間が増える．
括った範囲が行に収まらないときの挙動も別途確かめる必要がある．
規律で防げるうちは持ち込まない．

## 再現の手順

1. 幅を固定した段落へ，括弧の前の文字数を変えた検体を並べた HTML を書く．
2. `node_modules/.bin/vivliostyle build <検体>.html -o <出力>.pdf` で組む．
3. PDF を PyMuPDF で読み，行末の文字を調べる．

行の復元には注意が要る．
`get_text('dict')` のブロックは，インライン要素の境目で 1 行を複数へ割る．
スパンの `origin` の y 座標を許容差 2pt で束ね直すと，実際の 1 行が得られる．
この束ね直しをしないと，割れた断片の末尾を行末と誤って数える．
