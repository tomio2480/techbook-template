# PR に出ない lint 負債を片づけて分かったこと

Issue #176 で片づけた既存 lint 指摘について，計測の落とし穴と，
規則ごとの直し方の判断を記録する．PR #177・#178・#179 の 3 本で
textlint は 0 件になり，残るは上流判断待ちの `MD036` 21 件である．

## 計測は改行コードで変わる

Issue #176 は当初 textlint 95 件と書いていた．LF で数え直すと 86 件で
あった．差の 9 件はすべて `sentence-length` である．

Windows の作業ツリーは `core.autocrlf=true` で CRLF になる．textlint は
段落内の改行を空白として扱うため，`\r` が 1 文字ぶん文長へ乗る．
同じ木を CRLF へ戻すと 39 件に戻ることを確かめた．
他の規則の件数は改行コードで変わらない．

長さを見る規則だけがずれる．件数の食い違いに気づいたら，まず改行コードを
疑うとよい．CI は LF で検査するため，手元では `git archive` で木を
書き出してから数える．

## 文長にはコードとリンクの文字数も入る

`sentence-length` はコードスパンの中身も数える．リンクは表示文字列を
数え，URL は数えない．

`techbook-introduction-to-electronics-basic-led` は 45 字である．
これを含む文は，前後の語をどれだけ削っても 80 字へ収まらない．
長い識別子は主語や補足として別の文へ切り出すしかない．

コマンドも同じである．今回は 70 字のコマンド 1 件をコードブロックへ
移した．文の途中に置く形では上限へ収まらないためである．

## 行頭の全角括弧は折り返しの問題である

`ja-no-space-around-parentheses` の 12 件は，すべて継続行の行頭に
全角括弧か鍵括弧が来た箇所であった．括弧の使い方そのものは正しい．
継続行のインデント空白が，括弧前のスペースとして読まれる．

直し方は 2 つある．折り返し位置を変えて括弧を行の途中へ移すか，
括弧を外して地の文にするかである．強調だけを担っていた鍵括弧は
外すほうが読みやすくなった．

## 括弧を行またぎにすると別の規則が出る

折り返しを変えた結果，番号付きリストの項目で `（` と `）` が
別の行へ分かれた．すると `no-unmatched-pair` が出た．

段落の途中で行をまたぐ括弧は指摘されなかった．リスト項目とその継続行の
組み合わせでのみ再現した．括弧の対を 1 行に収めるか，括弧を使わない形へ
書き換えると消える．

## 残したもの

`MD036` の 21 件は本リポジトリでは直さない．2 種類が混ざっており，
どちらも中央テンプレートの設定で扱うほうが全 caller に効くためである．

- 既定の `punctuation` が `．`（U+FF0E）を持たないための誤検出．
- `README.md` が推奨する「太字の小見出し」．こちらは意図した書き方である．

上流 `tomio2480/github-workflows` へ #102・#103・#104 を出してある．
採否が出るまで待つ．
