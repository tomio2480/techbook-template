# ビルドが追跡ファイルへ残す目印と，改行コードだけの差分の切り分け

`build:print` が目次の追跡ファイルを書き換えたまま終わる不具合を直した記録である．
直した後も `git status` に `M` が残り，原因の切り分けが要った．
対象は Issue #111 と PR #120 である．

## 背景

`npm run build:print` は，改丁の面を伝えるクラスを各原稿の生成 HTML へ書き込む．
生成 HTML は Markdown から作り直されるため，書き込みは次のビルドで消える．

目次（`src/chapters/toc.html`）だけは事情が違う．手で書く追跡ファイルであり，
Markdown を持たない．後始末が戻さないため書き換えは残ったままになる．
これで作業ツリーが汚れていた．
さらに `injectHtmlClass` は既存の同名クラスを見ずに足す．
このため実行のたびにクラスが重複し，`print-side-verso` が増えていった．

## 復元をどこへ置くか

Issue は「`print.css` で目次の面を直接指定する」案を挙げていた．これは採らない．

`print.css` には「付いたクラスを面へ翻訳するだけで，区分の一覧は持たない」と
明記されている．面の指定は `config/book.yaml` を単一の出所とする設計であり，
CSS へ区分名を書くとこの設計を崩す．PR #94 のレビューで一度決めた形である．

代わりに，目印を入れる直前の中身を控え，`finally` で書き戻す形にした．
既存の `add-line-numbers.mjs --restore` と同じ後始末の枠へ収まる．
控えは `applyPrintMarkup` を呼ぶ直前に取る．ビルドが途中で失敗しても戻る．

## 対象をファイル名で決めない

復元の対象は「Markdown を持たない entry」とした．`toc.html` という名前で
判定していない．同じリポジトリの `hasChapterOpening` が
「ファイル名に依存させず，原稿を改名しても判定が壊れないようにする」と
書いているのに揃えた．利用者が別の HTML を直接置いた場合も同じ扱いになる．

`.gitignore` は `src/chapters/*.html` を除外しつつ `!src/chapters/toc.html` で
目次だけを追跡している．この構成が「Markdown を持たない HTML は追跡ファイル」
という判定と一致する．

## 残った M フラグの切り分け

修正後も `git status` は `toc.html` と `vivliostyle.config.js` に `M` を出した．
`git diff` は 0 バイトであり，内容は同じである．
Windows の作業ツリーは `core.autocrlf=true` で CRLF になるが，
ビルドが LF で書き直すため改行コードだけが食い違う．

これが本件由来かを確かめるため，変更していない `npm run build` を
きれいな木で実行した．同じ 2 ファイルに同じ `M` が出た．
よって既存の挙動であり，`build:print` の目印とは別である．

切り分けは 2 点で行う．内容差分が 0 バイトであること，未変更の経路で再現することである．
`M` が出たという観測だけでは足りない．直したはずの不具合が残っていると誤解しかねない．

## 代替案と棄却理由

最初のビルドの前に控えを取る案も検討した．こうすると Windows でも
`M` が出なくなる．しかし Vivliostyle による目次の正当な更新まで
打ち消してしまう．目次の更新は電子書籍用の `npm run build` が担う経路であり，
紙面用のビルドが握りつぶすべきではない．よって控えは目印を入れる直前に取る．

受け入れ条件の文言も，強い「追跡ファイルを書き換えない」ではなく
「紙面用の目印が残らない」とした．実装が保証できる範囲に合わせるためである．
